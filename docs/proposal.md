# 随车算作品策划案

面向 Rokid AI Glasses 的静默购物计价助手

技术路线更新版  2026年10月29日  原型基线 v0.7.0

随车算面向超市和会员店购物者，在选购过程中维护商品清单、件数与预计合计。目标体验是用户主动开启一次购物会话，正常查看和取放商品；信息充分时自动记账，存在疑问时通过眼镜上的短提示完成核对，减少反复掏手机和开口报数。

### 项目定位与本期交付

以 Rokid AI 赛道的生活类 AIUI 智能体为定位，采用沉浸式购物页面。首个验证场景选择山姆常见包装商品与已经称重贴签的商品，后续再扩展门店、价签和商品类型。核心任务是持续维护本次选购账目，而非仅给出一次识物回答。

| 项目 | 方案 |
| --- | --- |
| 产品目标 | 无声为主的取放记账、即时核对与购物摘要。预算可选，默认关闭。 |
| 最新路线 | AIUI 取图与交互 → 视觉模型理解 → 独立 OCR 读字 → 规则核验 → 本地账本 → HUD。 |
| 现有基础 | 购物逻辑与 Studio 界面已验证；独立 OCR 已在本机运行；真机完整链路尚待验证。 |
| 实施顺序 | 先验证拍照核价闭环，再验证连续取图和自动取放；空间跟随与戒指适配作为后续扩展。 |

## 02  使用场景与完整购物流程

首批用户是购物时需要估算总额、会反复比较和退换商品的个人消费者。眼镜的价值在于第一视角采集与随时可见的金额反馈：双手仍用于推车和拿商品，查看结果时无需再取出手机。是否真正减少操作负担，将通过同一购物任务的对照测试判断。

| 阶段 | 用户行为 | 目标响应 |
| --- | --- | --- |
| 开始 | 主动打开随车算，按需设置预算 | 建立购物会话，明确显示观察、暂停或待核对状态。 |
| 识别 | 查看商品包装和对应价签 | 建立商品身份与当前门店价格候选；未见入车动作不入账。 |
| 加入 | 将商品放入本次购物车或购物篮 | 取放、数量和价格均有充分证据时提交一次加入事件。 |
| 比较 | 临时拿起已购商品阅读，再放回车内 | 维持原账；不能因离开画面就扣减，也不能放回后重复累计。 |
| 退回 | 将已计入商品放回货架，或明确确认退回 | 匹配原账目并扣减；无法确定是哪一项时让用户选择。 |
| 结束 | 查看清单并完成本次购物 | 展示摘要、保存本地记录；需核对项仍明确保留。 |

### 优先覆盖的商品

第一类为有明确销售包装和对应售价的商品，例如一箱牛奶、一组酸奶或一袋燕麦。第二类为称重完成后贴有总金额标签的商品，例如独立包装的生鲜。销售单位以整包、盒、袋或箱为准，不把包装内可见的小件数量当作购买份数。

### 无法完整看见的动作

同行人从视野外加货、商品一直被遮挡或快速跨过镜头时，系统可能完全观察不到事件。首轮实测需分别记录可见动作和全部实际动作；后续增加漏记核对流程。现阶段用户仍可打开清单补充和修正，不能把画面中未发现变化解释为账目完整。

### 有限确认的过渡模式

连续观察尚未达标时，用镜腿触发拍照、确认候选完成静默购物；退回从清单中选择。它用于核价与账本验证，并保留可用体验。自动取放仍是研发主线，只有真实连续购物通过验证后才作为默认模式开放。

## 03  无声交互与眼镜界面

购物界面以预计合计、商品件数和最近几项为主要信息。已核价金额与待核价项分开表达，金额不完整时显示已核价小计及待核价件数。预算启用后再显示余额或超出金额，避免将预算设置变成使用前提。

| 交互 | 设计与实现边界 |
| --- | --- |
| 镜腿操作 | 选择、确认、返回和翻页作为基础路径，已有 Studio 映射验证；真机事件映射待核验。 |
| 点头确认 | 仅在核对卡激活并完成姿态校准后使用；普通走路和看货架不应触发确认。原型已接入，佩戴待测。 |
| 手势与语音 | 手指数用于补充数量，语音由用户主动唤醒；均为可选入口。当前语音以有限购物指令为主。 |
| 新款 Rokid Ring | 预留选择、确认与返回的输入适配层；取得官方接口并完成实机验证后接入。 |
| 显示与反馈 | 采用单绿信息层级、有限短提示和稳定布局；首版 HUD 固定于视野，不依赖购物车空间锚定。 |

### 减少打断的具体规则

已核实的动作提交后只给简短加减提示，并保留撤销入口；需要核对时展示商品短名、数量、价格来源及一个明确问题。候选不会因为等待超时自动确认。编辑期间暂停视觉提交，避免用户改价时又收到过期的自动记账结果。

正常购物不主动播报、不打开应用麦克风。主动语音处理完成后按此前状态恢复；用户明确暂停后保持暂停。采集指示和系统权限遵循设备行为，“静默”仅指无须说话与无主动播报。

## 04  系统架构与能力分工

工程采用 AIUI Page、WXML、WXSS 与 JavaScript 模块，购物状态由应用维护。模型负责提出候选，规则层决定候选是否可采纳，账本负责金额和数量。商品识别、动作识别与财务计算分开，便于定位错误并替换识别组件。

| 层级 | 职责 | 运行位置 |
| --- | --- | --- |
| 采集与交互 | 相机、镜腿事件、可选语音与姿态；呈现清单及核对卡 | AIUI 宿主与眼镜页面 |
| 场景理解 | 判断包装身份、候选标签、数量和拿放状态，输出带帧号的结构化候选 | 宿主配置的图像模型 |
| 独立读字 | 返回同一张图片的文字、位置与读字分数，提供另一条价格和规格证据 | 外部 OCR 服务 |
| 证据核验 | 关联商品与标签，检查金额栏目、规格、帧号和动作连续性 | 应用规则模块 |
| 购物账本 | 唯一事件入账、整数分计算、数量与优惠重算、撤销和恢复 | 应用本地模块与存储 |

### 数据如何形成一笔账

授权画面 → 图像模型候选与独立 OCR → 商品及价签对应 → 动作事件 → 价格和数量校验 → 提交账本 → HUD 更新。任一必要证据缺失时进入核对；请求失败、无价签或读字冲突时，不使用模型猜测的金额补齐。

### 官方接口与项目自研的边界

当前官方资料列出相机采集、图像模型、网络请求与存储等接口，但没有可直接使用的商品入车计价能力。单次拍照采用 wx.media.createCameraContext().takePhoto；连续观察原型采用 getUserMedia 与 ImageCapture。接口存在不等于目标机型有权限或能持续运行。[2][3]

图像理解经 LanguageModel 调用宿主配置，不在策划案锁死某一商业模型。识别质量、耗时与费用要记录实际模型及运行环境后比较；LanguageModel.availability 返回可用，也不能替代图像能力实测。[4]

### 部署分工

OCR 当前使用 RapidOCR、PP-OCRv6 small 与 ONNX Runtime，在电脑本地服务运行。真机阶段需迁移到设备可达且受鉴权保护的 HTTPS 服务；不把眼镜的 localhost 当作开发电脑，也不把 OCR 模型塞进 AIX 包。手机承担平台需要的连接或网络协同，日常购物操作以眼镜端为主。[5][6]

## 05  商品身份与价格核验

商品身份、标签对应和价格栏目必须同时成立。视觉模型寻找正在操作的包装与标签候选；独立 OCR 读取同一图片的文字及区域；规则层检查品牌、品名、口味或型号、销售规格与金额。两种结果一致只是一项证据，仍可能共同犯错，不能直接解释为正确概率。

| 场景 | 核价规则 |
| --- | --- |
| 普通货架价签 | 核对对应商品及整包规格，区分相邻价签；不能只凭空间接近或最大的数字定价。 |
| 称重后贴签 | 识别当前包装上的总金额，作为这一包的价格。重量和每公斤单价用于核对，避免重复相乘。 |
| 同名不同规格 | 规格、口味或销售单位不一致即保留疑问；多包装套组不能按内含小件重复计价。 |
| 会员与优惠 | 条件不清时请用户确认。原型已有第二件半价规则；满减、券后价和复杂组合优惠不自动推导。 |
| 冲突或缺字 | 重拍包装与价签，或人工输入单价；独立 OCR 不可达时保留待核价，不回退到模型猜价。 |

### 一包称重商品的例子

测试标签显示净重0.752千克、单价59.80元每千克、总金额44.97元。系统应把该包记为44.97元，而非再次乘0.752。若下一包为另一重量和金额，应单独保留该包价格或价格批次；不能因为商品名称相同而沿用上一包总价。以上数字仅用于规则说明。

### 防止旧画面与伪造证据入账

OCR 客户端校验请求号与帧号，只短时复用完全相同图片的读字结果。模型自行输出的“已通过 OCR”不被接受。当前短时缓存并非商品价格库；未来若加入同商品价格复用，仍需约束门店、规格、有效时间和价格来源，称重贴签商品必须逐包核对。

### 训练策略

先使用现成 OCR 与宿主视觉模型积累真实错误样本，不从零训练通用模型。若主要问题来自错读小字，优化图像质量和文字区域；若主要问题来自错配标签或丢失动作，再评估专用检测与跟踪。微调须建立训练、调参与独立验证的样本隔离，不以演示样本成绩代替泛化能力。

## 06  连续取放与可靠记账

自动记账依据同一商品的状态变化。看到商品、拿起商品和商品离开画面都不单独构成购买或退回。对一件商品，原型用货架、手持、车内等观察状态组成事件，再检查是否具有足够的连续证据。

| 观察过程 | 目标处理 |
| --- | --- |
| 货架 → 手持 → 车内稳定 | 包装、数量与价格明确后新增一次；事件编号用于防止重复提交。 |
| 车内 → 手持 → 车内 | 保持原数量，属于查看或整理。 |
| 车内 → 手持 → 货架稳定 | 对应原账目明确后扣减；不能匹配唯一条目时进入选择核对。 |
| 拿起后遮挡或去向不明 | 中断自动判定，保留待核对，不将消失直接当作退回。 |
| 多种商品快速同时移动 | 作为高风险场景收集样本；当前单组追踪不能保证逐 SKU 独立处理。 |

### 现有原型与下一步改进

v0.7.0 默认约每1.4秒取一张图，每批三张并带上一批衔接图进行判断。这是抽帧原型，不是高速视频跟踪；队列、超时和会话销毁用于限制资源占用。现有帧数、时间窗口与模型分数规则尚未经过真实数据校准。

先测正常走路、转头、推车时能否看见完整动作，以及实际取图间隔、推理时延和丢帧情况。若满足基本覆盖，再开发画面变化筛选与事件窗口采样，减少对静止货架的重复分析；这些调度优化尚未作为已完成功能交付。

### 连续采集不成立时的处理

wx 单次拍照文档要求交互调用，不能据此承诺无交互循环拍照。若目标宿主的 MediaStream 路径不可用，先交付镜腿触发的核价模式，并向官方核实支持的连续采集方式。原生 SDK 只能作为另行验证的备选路线，切换前须确认 AIUI 参赛与分发要求，不能直接承诺混合部署。[2][3]

### 本地账本与异常恢复

金额按整数分计算，添加、退回、数量和单价修改都进入确定性计算。失败与迟到结果不能越过当前会话状态写账。断网或离开页面时停止在线识别并保留清单；恢复网络后由用户主动继续。当前未实现自动购物车盘点和小票差异核对，结束前保留人工检查清单。

## 07  原型进展与验证证据

目前已具备可运行原型，验证层次分为逻辑测试、模拟调试、本机 OCR 与真机购物。以下状态截至2026年10月29日，以 v0.7.0 工程和验证记录为准。

| 模块 | 现有结果 | 仍需验证 |
| --- | --- | --- |
| 清单与金额 | 添加、退回、数量与单价修改、撤销、可选预算、摘要及最近10次记录已实现 | 真实购物过程中的纠错负担与恢复体验 |
| 自动化检查 | 104项测试通过，21个源文件检查通过，AIX已打包 | 测试含模拟接口与合成夹具，不证明视觉准确率 |
| Studio 界面 | 购物流程已有模拟验证，v0.7.0沉浸式首屏启动正常 | 最新 OCR 核价全链路尚未在 Studio 验证成功 |
| 拍照与模型 | 原生拍照路径取得本地测试图片并进入宿主模型 | 曾把1.8千克识别成1.35千克；补充规格 OCR 校验后仍需复测 |
| 独立 OCR | 本机真实处理5张参考图；HTTP客户端调用已验证 | 缺包装与价签同框的真实正例；小字品牌存在错读 |
| 眼镜与输入 | 相机、点头、手势和语音相关原型已接入 | 尚无眼镜、连续购物或新款戒指实测结果 |

### OCR 耗时的正确解读

5张已有商品或购物车参考图的本机 OCR 推理耗时约0.27至1.02秒。这些耗时不含模型初始化、眼镜取图、网络传输和图像大模型，也未构成识别准确率测试，因此不用于承诺眼镜端响应速度。

### 现阶段仍缺的功能

自动漏记核对、多 SKU 并行追踪、复杂优惠解析和通用上下文指令理解尚未完成。诸如“刚才那盒换成另一个规格”的表达，需要额外的指代解析及操作确认。HUD 跟随购物车和新款 Rokid Ring 均为后续方向。

### 公开展示口径

演示图标明 Studio 模拟截图，真实图像测试标明输入与结果。最终拍摄真机购物视频时保留核对和失败恢复步骤，不以预置清单、生成画面或模拟动作冒充真实自动识别。项目报告可展示产品进展，源码维持现有私有管理。

## 08  设备验证与验收计划

验证围绕“眼镜能看见、系统能分清、账本不重复、用户能纠正”展开。先用真实包装、价签与第一视角素材验证识别，再用借测眼镜检验实际权限、画面覆盖和持续使用表现。所有指标报告样本量、失败类型与测试环境。

| 验证阶段 | 方法与建议样本 | 进入下一阶段的依据 |
| --- | --- | --- |
| 真实素材 | 首轮30种商品、至少100组包装与价签图；加入相邻标签、同名不同规格、反光和称重贴签 | 建立逐项人工真值，保留独立验证集；错误能定位到身份、标签或金额环节 |
| 设备能力 | 目标机型测试单次取图、连续采集、镜腿、联网与权限拒绝；记录固件和 App 版本 | 实际图片可解码、字可读、服务可达；明确哪些能力可用于当前宿主 |
| 连续动作 | 至少100个加入、退回、查看及遮挡事件，区分可见动作与画面外事件 | 能重现误加、漏记和重复提交；无法可靠处理的场景有可用核对路径 |
| 购物体验 | 同一购物清单对比手机手记、镜腿确认和自动模式；至少5轮20至30分钟场景测试 | 记录纠错、确认次数和耗时；自动模式确实降低操作负担 |
| 故障恢复 | 断网、模型超时、OCR不可达、页面隐藏、重启及迟到响应 | 停止采集后不继续写账；清单恢复正确；未核价项不会伪装成完整总价 |

### 需要分别报告的指标

身份匹配、价签匹配与金额正确率分别统计；自动提交统计精确率，事件识别分别统计可见事件召回和全部实际事件覆盖。额外报告错误自动入账笔数、重复笔数、漏记件数、待核对比例、每件人工操作次数，以及端到端耗时的中位数和 P95。

连续使用记录眼镜和手机耗电、发热、网络条件、每次购物的模型请求数量与费用。相同图片缓存命中率单独统计，不把缓存速度混入首次识别耗时。

### 开放自动模式的门槛

受控账本回归必须与人工预期一致，重复回调和网络重试不能产生重复账目。遇到无价、错规格和证据冲突必须拦截自动提交。若独立验证仍出现无法解释的自动错账，或核对负担高于镜腿确认模式，则继续限制自动模式范围，修复并重新测试；不提前宣称通用商超可用。

## 09  研发计划与运行安排

采用按验证结果推进的里程碑。以下周期为单人研发的工作量估计，不含设备寄送、平台答复、素材采集授权与审核等待；具体日期随设备到位调整。

| 里程碑 | 预计工作量 | 交付与决策 |
| --- | --- | --- |
| M1 能力确认与素材 | 3至5个工作日 | 确认借测机型与接口；准备真实货架样本、动作标注和验证脚本。 |
| M2 核价闭环 | 5至8个工作日 | 部署受保护的 OCR 服务，完成眼镜拍照到候选核对、入账与撤销；保留失败样例。 |
| M3 自动取放验证 | 7至12个工作日 | 验证连续取图、状态关联与去重；据结果决定是否需要专用检测和跟踪模型。 |
| M4 体验与恢复 | 4至6个工作日 | 补足漏记提示、易用纠错和异常恢复；评估点头与手势是否值得保留。 |
| M5 参赛交付 | 3至5个工作日 | 冻结可验收范围，准备真机视频、作品PPT、测试说明及商店提审材料。 |

### 必要资源与成本测量

需要一套与本届 AIUI 兼容的眼镜及配套手机环境、可访问的 OCR 服务、模型调用额度，以及可反复采集的真实商品与价签。新款戒指不列为前期必需品。服务费用以实际请求量、单次图像成本和使用时长估算，不预设免费长期运行。

运行目标是用户无需逐件操作手机。OCR 与模型推理作为辅助服务，账本和界面保持本地响应；平台联网方式、图像上传大小和限流策略通过官方确认与真机测试确定，避免将开发电脑作为必须随身携带的终端。

### 数据与隐私

用户主动开始后才采集；暂停、离开页面和结束购物时停止。应用与随附 OCR 服务当前不持久保存照片，使用短时内存缓存；核价画面将发送给配置的 OCR 服务和宿主模型。宿主及供应商的数据保留策略需单独核实，不能把应用不落盘表述为全链路零留存。

测试素材按用途取得许可并去除无关个人信息。服务启用 HTTPS、鉴权、访问限制与请求限额，密钥不放入代码仓库或公开包。购物记录保存在本地，后续提供用户可见的清理入口。

### 扩展顺序

核价与取放可靠后，再评估上下文购物指令、漏记盘点、小票核对和复杂促销。线上比价、车旁空间 HUD 与戒指交互单独立项，不加入首版验收依赖。

## 10  参赛说明与资料依据

### 从既往案例中调整的关键点

参考的2025年参赛帖子展示了物体识别、目标设备、赛道及空间能力方面的沟通问题。该帖属于当事人公开的历史经历，不代表2026年官方接口或审核结论。本项目据此明确采用 AIUI 生活类路线，把自研识别与官方能力分开说明，并在借测阶段确认关键技术依赖。[1][7]

### 借测申请可用简介

随车算是面向 Rokid AI Glasses 的静默购物计价智能体，目标是在超市选购时记录商品取放、件数和预计金额，信息不确定时以眼镜核对卡补充确认。目前已完成 AIUI 购物原型、模拟交互及独立 OCR 本机验证，申请设备用于检验第一视角价签清晰度、连续取图可用性、视觉模型与 OCR 完整链路，以及镜腿交互和持续购物体验。

### 向平台确认的事项

确认借测机型及配套版本；AIUI 前台连续取图的权限、频率与生命周期限制；宿主模型的图像能力、请求大小及额度；外部 HTTPS OCR 的网络与鉴权方式；静默视觉交互的提审要求。记录官方答复后更新实现，不把历史帖子或模拟器结果当成设备能力承诺。

### 最终交付

按本届 AI 赛道要求准备可在眼镜与 AI APP 上运行的智能体、作品介绍 PPT、真机演示视频及简短测试说明，分别完成商店提审和赛事资料提交，并按规则准备 AI APP 社区参赛内容。当前策划案与 GitHub 报告不替代上述交付；正式提交前再核对规则。[1]
